# Feature Specification: Multi-Agent Dispatch (M1)

**Feature Branch**: `018-multi-agent-dispatch` (trunk-based: logically isolated under this directory)
**Created**: 2026-10-19 | **Status**: Draft (specification half only; implement/validate wait for F14 and F17)
**Input**: "Modo multi-agente real via subagentes do host guiados por manifest (opcao M1)" (`.spec-master/context/app-features.md`, Ciclo 2, Feature 18) + USER DECISION (EXPLICIT, 2026-10-19): multi-agent = the harness proposal's subagents `sm-spec`, `sm-implement`, `sm-review` (docs/harness-reformulation/proposal.md, Wave 2) generated by `packaging.py` for the 8 hosts; one dispatch manifest per wave built from `worktree waves` + `PhaseResult` (<= 2k tokens per result); agent cap per wave; per-worktree governance in `hookd`. Team Mode stays frozen.

## Grounding (DISCOVERED_FROM_CODEBASE)

- `worktree.compute_waves(ordered)` groups `{id, dependencies}` into waves; `plan_worktree` creates detached/branch worktrees under `.spec-master/worktrees/<id>` (idempotent, skips single-feature waves and non-git repos); `aggregate`/`conflicts` fold results and never merge (`spec-master/lib/worktree.py`).
- `team_model.build_workstreams(features)` yields packages `{id, feature_id, owner_agent, reviewer_agent, depends_on}` (no implicit chaining after F13); `assign_peer_review(owner)` returns a different agent; `risk_profile._reviewer_for` falls back to `architect`. `team_workstreams` records review/integration verdicts and `aggregate_with_verdicts` (Tech Lead gate).
- `phase_result.parse_last_phase_result(text)` is the only PhaseResult parser (accepted values `artifact_updated | no_changes_required | user_decision_required | failed`).
- `packaging.py` renders every host manifest/hook/skill from one source (`render()`, `check()`, `generate()`); `doctor` fails on drift. Hosts: `kernel/hosts.HOSTS = claude, qwen, codex, copilot, gemini, cursor, kiro, antigravity`.
- `kernel/hookd.py` has a `subagent-stop` handler that allows everything ("subagents are not governed yet"); `project_root(payload)` resolves the root from env/`cwd`; decisions go to `.spec-master/hooks/decisions.jsonl`.
- `docs/contracts/token-ledger-v1.md` §1 fixes `agent.started` / `agent.finished` (`agent_id`, `agent_type`, `worktree`, `transcript_path`) in `.spec-master/events.jsonl`, and §2/§3 the per-`agent_id` ledger and `by_agent` aggregate. F14 PRODUCES them; this feature CONSUMES them and writes no second event format.
- Proposal §5.6 / Wave 2: the Standard lane runs implement and review in subagents returning `PhaseResult` <= 2k tokens; Patch never uses subagents; "do not parallelize before there is a lock and evals".
- Budgets (`doctor run --errors-only` must exit 0): `kernel/` has ~56 LOC of headroom (orchestrator brief), hook path <= 1500 LOC and 100 ms p50 (825 LOC / 34 ms now), cards <= 3 KB. New code lives OUTSIDE `kernel/`.

## Re-scope (INFERRED, reason recorded)

`rescope.md` "Remaining delta" and the USER DECISION above REPLACE the original criteria where they conflict: (a) "adapter launches subagents" becomes "packaging generates `sm-*` subagent definitions per host; the host's subagent tool launches them from the manifest" (the core never spawns processes); (b) "playbook" per package is the role playbook under `spec-master/knowledge/playbooks/`; (c) tokens and results come from F14 `agent.finished` + ledger, not from a new "subagent-stop" writer here; (d) the manifest is built from `worktree waves` over work packages (plus `PhaseResult`), not a new scheduler; (e) Team Mode (12 personas, 6-step template) is frozen: dispatch reads its packages but changes none of its code or behaviour.

## Clarifications

### Session 2026-10-19 (autonomous, nothing blocking)

- Q: Wave unit? -> A: `worktree.compute_waves` over WORK PACKAGES (from `.spec-master/workstreams.json`, else `team_model.build_workstreams` over the feature's tasks with `owner_agent`/`depends_on`); a package with `depends_on` lands in a later wave (INFERRED).
- Q: Default and bounds of the agent cap? -> A: `dispatch.max_agents` in `.spec-master/policy.json`, default 4, valid 1..8; overflow packages are split into ordered `batches` of the same wave, never dropped (INFERRED from "default 3-5").
- Q: Which subagent runs which package? -> A: implementation packages -> `sm-implement` (test-first); one read-only `sm-review` entry per package, eligible only after its owner's result is recorded; `sm-spec` for spec-phase packages only in the Standard lane (INFERRED, proposal §5.6).
- Q: Reviewer != owner? -> A: two checks: persona (`reviewer_agent != owner_agent`, reusing `assign_peer_review`) AND identity (reviewer is a separate `sm-review` invocation with a clean context and a different `agent_key`). A verdict by the owner is refused (INFERRED).
- Q: Model/effort per entry? -> A: read the F15 ceremony-profile hint when present (`model`/`effort` keys of `risk_profile.profile_for`); absent -> `null` meaning "host default"; dispatch never hardcodes model names (INFERRED, depends on F15).
- Q: How is the 2k-token result cap enforced? -> A: the `sm-*` definitions instruct one final `phase_result` JSON block; `dispatch result` parses it with `phase_result.parse_last_phase_result`, keeps an allow-listed shape (`phase_result`, `summary`, `files`, `questions`, `evidence`), truncates the serialized record to 8000 chars (~2k tokens, chars/4 estimate) and sets `truncated: true` (INFERRED).
- Q: Per-worktree governance mechanics? -> A: `dispatch prepare` writes `.spec-master/dispatch/scope/<agent_key>.json` in the MAIN root and a `.spec-master/worktree.json` marker `{main_root, agent_key, package_id, role, owned_paths, read_only}` in the worktree. `hookd` (one lazy hook point) loads `lib/dispatch_scope.py` only when the marker exists: writes outside `owned_paths` -> DENY; `sm-review` read-only; `git merge|push|rebase|worktree remove|branch -D` and writes to `state.json`, `workstreams.json`, `policy.json` -> DENY. Enforcement follows `hooks_mode` (audit logs, block denies) (INFERRED; reuses `policy`/`paths`).
- Q: Hosts without a documented plugin-shipped subagent format? -> A: `packaging` generates agent files for claude, qwen, copilot, cursor, gemini (Markdown + frontmatter) and codex, kiro (host-specific format); where the format cannot be shipped in the plugin (agent-plugins root, antigravity) the manifest's `fallback_instructions` give sequential steps. Exact per-host file formats are verified at implement time against host docs and recorded in `contracts/host-agents.md` (open question, non-blocking: spec holds the defaults).
- Q: Merge authority? -> A: unchanged and gated. `dispatch` never runs `git merge`; integration stays `workstreams review` -> `workstreams integrate` (Tech Lead) -> a human; `dispatch aggregate` is `worktree.aggregate` + `conflicts` (report only) (EXPLICIT: app-features criterion 5).

## User Scenarios & Testing

### US1 - Operator gets a wave manifest (P1)
`python3 spec-master/lib/cli.py dispatch manifest --feature F --wave 0` prints a JSON manifest the host's main session can execute.
1. Given a feature whose tasks have owners and `depends_on`, When the manifest is built, Then each entry has `package_id`, `role`, `playbook`, `model`, `effort`, `worktree`, `owner`, `reviewer`, `owned_paths`, `card`, and `reviewer != owner`.
2. Given 7 independent packages and cap 4, When built, Then `batches` = [4, 3] in order and no package is lost.
3. Given a package depending on another, Then it appears in a later wave.
4. Given a single-package wave or a non-git repo, Then no worktree is planned (`worktree: null`, runs in place).

### US2 - Subagents run isolated and bounded (P1)
1. Given a prepared wave, When the host launches `sm-implement` for package P, Then it runs in P's worktree, writes only `owned_paths`, and its final message is one PhaseResult block.
2. Given a result larger than the cap, Then `dispatch result` stores a truncated, allow-listed record and flags `truncated`.
3. Given a subagent writes outside `owned_paths` or touches `state.json`, Then hookd denies (block mode) or logs (audit mode), with the `agent_key` in the decision.

### US3 - Results, tokens and review are traceable (P1)
1. Given F14 events, When `dispatch status --wave N` runs, Then each entry shows start/finish from `agent.started`/`agent.finished` and tokens from `tokens summary` `by_agent`; missing producer data -> `null`, never invented.
2. Given an owner's package finished, Then its `sm-review` entry becomes eligible only after the owner's result is recorded; a verdict by the owner is refused.

### US4 - Nothing is merged automatically (P1)
`dispatch aggregate` reports changed files, conflicts and verdict states per worktree and stops; integration requires the existing `workstreams review|integrate` verdicts and a human.

### US5 - All hosts get the subagents (P2)
`packaging.py generate` renders `sm-spec`, `sm-implement`, `sm-review` for every host that can load plugin-shipped agents; `check` fails on drift; `doctor` stays green.

## Requirements

- **FR-001**: `dispatch.build_manifest(root, feature_id, wave_index, max_agents=None)` returns schema `spec-master.dispatch/v1` (`contracts/dispatch-manifest.md`) from `worktree.compute_waves` over work packages and `team_model` owners/reviewers; pure, deterministic, no writes.
- **FR-002**: Entry fields: `agent_key`, `package_id`, `feature_id`, `role`, `card`, `playbook`, `model`, `effort`, `worktree`, `branch`, `owner`, `reviewer`, `owned_paths`, `depends_on`, `result_path`.
- **FR-003**: Cap: argument > `policy.json dispatch.max_agents` > default 4; outside 1..8 is rejected with a clear error; overflow becomes ordered `batches`.
- **FR-004**: `reviewer != owner` (persona) and a review entry is a separate `sm-review` invocation; `dispatch result --role sm-review` refuses an `agent_key` equal to the owner's.
- **FR-005**: `dispatch prepare` creates worktrees via `worktree.plan_worktree` (no second implementation), writes scope records and the worktree marker; idempotent.
- **FR-006**: `dispatch result --package P --text-file F` parses with `phase_result.parse_last_phase_result`, caps at 8000 chars, allow-lists fields, writes `.spec-master/dispatch/<feature>/<wave>/<package>.json` atomically, and updates nothing else.
- **FR-007**: `dispatch status` joins manifest + results + `events.jsonl` (`agent.*`) + `tokens summary` `by_agent`; absent producer data -> `null` plus a note; read-only.
- **FR-008**: `dispatch aggregate --wave N` = `worktree.aggregate` + pairwise `worktree.conflicts` + `team_workstreams.integration_state`; never merges, rebases, pushes or removes a worktree.
- **FR-009**: `hookd` per-worktree governance via one lazy hook point calling `dispatch_scope.decide(root, payload, verdict)`; zero extra imports when no marker exists; `kernel/` growth <= 20 LOC.
- **FR-010**: `packaging.py` renders `sm-spec`, `sm-implement`, `sm-review` for every host that supports plugin-shipped agents, plus `fallback_instructions` text for the rest; bodies point to cards (<= 3 KB) instead of embedding protocol; `sm-review` has read-only tools; `sm-implement` is test-first.
- **FR-011**: Standard/Critical lanes only: `dispatch manifest` refuses Patch (no subagents) and features whose F17 lane is not Standard/Critical, unless `--force-lane` with a recorded reason (INFERRED, proposal §5.6).
- **FR-012**: Telemetry is consumed, not produced: relies on F14 `agent.started`/`agent.finished` (`agent_id`, `agent_type` = role, `worktree`) written by hookd `subagent-stop`; F18 only adds the governance verdict to the decision log.
- **FR-013**: Team Mode code and tests unchanged; native mode unchanged; `test_protocol_conformance` and `doctor run --errors-only` stay green; `dispatch` is NOT imported from the step API path.
- **FR-014**: Docs: add a short "Multi-agent dispatch" section to `spec-master/PROTOCOL.md` Step 6 and README usage; `spec-master/docs/team-mode.md` stays frozen; documented CLI invocations exist in the parser.

## Success Criteria

- **SC-001**: manifest/cap/reviewer/result/aggregate unit tests (offline; temp git repos for worktrees) pass.
- **SC-002**: `python3 -m unittest discover -s spec-master/tests` passes; existing worktree, workstreams, phase_result, team_model, hookd and packaging tests pass unchanged.
- **SC-003**: `doctor run --errors-only` exits 0 (kernel budget, hook path, packaging drift, cards).
- **SC-004**: hookd p50 changes < 5 ms when no marker exists.
- **SC-005**: replay of one Standard-lane wave (>= 3 packages) records per-agent tokens through F14 and shows review by a different agent (measured at validate).

## Non-goals

Spawning host processes from the core; auto-merge or auto-integration; Team Mode changes or new personas; parallelizing Patch; agent teams; producing events/ledger (F14); defining the Standard lane (F17); a UI (F16 consumes `agents`).
